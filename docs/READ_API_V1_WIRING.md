## How It Works

The frontend does not call `/api/v1/...` URLs directly. Because this MVP uses Supabase directly, each read endpoint is implemented as a Supabase RPC function.

```text
React page
  -> TanStack Query hook
    -> src/lib/api/*
      -> supabase.rpc(...)
        -> Postgres function
          -> tables/views
```

Example:

```ts
import { getDashboardSummary } from '../lib/api'

const data = await getDashboardSummary({
  period_start: '2026-04-01',
  period_end: '2026-04-30',
})
```

This calls:

```text
supabase.rpc('api_dashboard_summary', {
  p_date: null,
  p_period_start: '2026-04-01',
  p_period_end: '2026-04-30'
})
```

## Required Supabase RPC Functions

Create these functions in Supabase SQL:

```text
api_dashboard_summary(p_date, p_period_start, p_period_end)
api_ponds_list(p_include_inactive, p_q)
api_pond_detail(p_pond_id, p_logs_limit, p_stock_limit)
api_stock_movements(p_period, p_start_date, p_end_date, p_pond_id, p_type, p_limit, p_cursor)
api_cash_summary(p_month)
api_cash_transactions(p_month, p_type, p_category_id, p_limit, p_cursor)
api_cash_categories(p_type)
api_form_options()
api_profile_me()
```

Each function should return `jsonb` matching `docs/API_CONTRACT_V1.md`.

## Why RPC Instead Of New Tables

RPC functions are not new business tables. They are read endpoints inside Postgres.

```text
Business tables:
  units
  cycles
  log_harian
  stock_movements
  penjualan
  kas
  kas_categories

Read API functions:
  api_dashboard_summary(...)
  api_ponds_list(...)
  api_pond_detail(...)
  ...
```

Views/RPC can summarize, join, filter, and format data without forcing the frontend to know every table relationship.

## Current Frontend Contract Rules

- Use `description`, not `notes`.
- Do not use `water_condition`; the newest schema removed it.
- Use `kas.category_id`, with names loaded from `kas_categories`.
- Do not write `penjualan.total_rp`; it is generated by the database.
- Live stock should come from `stock_movements`, not `fish_inventory`.
